# Pro 1.16.0-pro — Shared NpgsqlDataSource Overload (Plan Skeleton)

**Status:** Skeleton (archived for cross-repo pickup) · **Date:** 2026-04-28
**Owner:** Asterisk.Sdk.Pro repo
**Trigger:** R5.5 Phase C-L `presence` sweep findings + ADR-0015 Phase 2

## Goal

Eliminate the architectural sprawl exposed by R5.5 Phase C-L: when Platform.Api initializes with all Pro features active and a single `ConnectionStrings:Postgres` value, **14 separate `NpgsqlDataSource` singletons** are created (each with its own connection pool). ADR-0015 Phase 1 mitigation in Platform v1.14.5 caps per-pool size at 10 to keep total demand ≤ 140 conns; Phase 2 collapses the 14 pools into **1 single shared pool** by allowing operators (i.e., Platform.Api) to inject a pre-built `NpgsqlDataSource` instance into all Pro storage packages.

## Acceptance criteria

1. **Each Pro storage package gains an additive overload:**

   ```csharp
   public static IServiceCollection UsePostgresXyzStorage(
       this IServiceCollection services,
       NpgsqlDataSource dataSource);
   ```

2. **Existing `(IServiceCollection, string)` signature is preserved verbatim** — binary-compatible. The string overload's body becomes:

   ```csharp
   public static IServiceCollection UsePostgresXyzStorage(
       this IServiceCollection services,
       string connectionString)
   {
       var dataSource = NpgsqlDataSource.Create(connectionString);
       return services.UsePostgresXyzStorage(dataSource);  // delegate to new overload
   }
   ```

3. **DbContext classes (Dialer, Analytics, EventStore, Realtime) take `NpgsqlDataSource` by ctor** instead of building from string. The string-taking ctor remains for tests/back-compat but is marked obsolete via `[Obsolete]` for Pro 2.0.0-pro removal.

4. **Pro.Push migrates to the additive overload pattern** — `TryAddSingleton(_ => NpgsqlDataSource.Create(connectionString))` becomes `services.TryAddSingleton(dataSource)` when the new overload is used; string overload preserves existing behavior.

5. **Test coverage:** each Pro package's existing storage tests pick up a 2-test boundary set:
   - `Use*Storage_WithDataSource_ShouldShareInstance` (passes shared instance, verifies same DataSource lives in DI)
   - `Use*Storage_WithConnectionString_ShouldStillWork` (legacy path still produces a working DataSource)

6. **Platform.Api adoption (subsequent release, e.g. v1.15.0):**

   ```csharp
   var coreDataSource = new NpgsqlDataSourceBuilder(coreConnectionString).Build();
   services.AddSingleton(coreDataSource);

   services.AddPostgresStorage(coreDataSource);          // Platform side
   services.UsePostgresDialerStorage(coreDataSource);    // Pro packages
   services.UsePostgresClusterTransport(coreDataSource);
   services.UsePostgresRealtimeStorage(coreDataSource);
   services.UsePostgresEventStore(coreDataSource);
   services.UsePostgresAnalyticsStore(coreDataSource);
   services.UsePostgresProAnalyticsLive(coreDataSource);
   services.AddProAgentAssistPostgres(coreDataSource);
   services.AddProCallAnalyticsPostgres(coreDataSource);
   ```

   When all stores share the same `coreDataSource`, demand collapses from 14 × pool size to 1 × pool size. The `ConnectionStringDefaults.ApplyPoolDefaults` Phase 1 helper stays in place but its effect on Phase-2 deployments is mostly nominal (the single shared pool inherits the conn-string-specified pool size; defaults still apply if absent).

7. **Compatibility matrix documented in Pro CHANGELOG:**
   - Pro 1.16.0-pro consumers compiling against the string overload: NO CHANGE
   - Pro 1.16.0-pro consumers using the new DataSource overload: opt-in, NEW
   - Platform.Api v1.14.x: continues to use string overload + ConnectionStringDefaults Phase 1
   - Platform.Api v1.15.x (post-Pro 1.16.0-pro): adopts DataSource overload

## Out of scope

- **PgBouncer integration** — already rejected in ADR-0014 §"What NOT to do" (breaks Pro.Push `LISTEN/NOTIFY`).
- **`NpgsqlMultiHostDataSource` for read-replica routing** — separate concern (capacity-planning.md Large+ tier).
- **Per-package `NpgsqlDataSourceBuilder` config hook** — already supported via the string overload's connection-string parameters; the new DataSource overload simply accepts a pre-built instance, which the operator built however they liked.

## Risks

- **Backward compatibility of DbContext string ctor obsoletion** — third-party code instantiating `DialerDbContext("connstr")` directly would emit warnings (and TreatWarningsAsErrors would fail). Mitigation: only mark `[Obsolete(IsError = false)]` for Pro 1.16.0-pro; promote to `IsError = true` in Pro 2.0.0-pro.
- **Operator confusion between the two overloads** — addressed by clear CHANGELOG + docs example showing the shared-DataSource pattern as the recommended Phase 2 default.
- **Pro test infrastructure** — some Pro storage tests directly instantiate DbContexts in test fixtures. Audit for these and update to use the DataSource overload directly.
