# Plan — Typification P0: cascading + conditional disposition forms (MANUAL)

## Context

**Por qué.** La tipificación de Verbara hoy es una **lista plana de selección única** + notas libres (`Disposition` tenant-scoped + `DispositionCode` de campaña en Pro). No permite **formularios complejos con respuestas entrelazadas** (cascada categoría→subcategoría→motivo + campos condicionales) que necesitan salud, soporte multi-producto y operaciones outbound. La investigación de mercado (ADR-0029) confirma que cascada+condicional+estructurado+IA es estándar esperado, hilado por **una sola taxonomía de motivo-de-contacto** end-to-end (IVR→enrutar→screen-pop→pre-llenar→tipificar→automatizar→analítica). Verbara ya tiene ~75% de la infraestructura (motor de Flows con `http_request`, contexto canal/cola/campaña, stack de IA con `CallSummary.DispositionCode`, `TagSource.AutoAi`).

**Qué entrega P0.** El **núcleo cascada + condicional MANUAL**: modelo jerárquico+condicional, baseline de migraciones limpio, CRUD + diseñador, binding por cola/campaña/canal/dirección + default tenant, `<DynamicTypificationForm>` en el wrap-up. Cierra la cabecera "formularios complejos con respuestas entrelazadas". P1 (captura compartida IVR), P2 (IA auto-disposition), P3 (data-dips externos), P4 (analítica + builder drag-drop) son fases posteriores; el modelo de P0 ya las hospeda (taxonomía compartible, campos con refs IA/data-dip, submission con campos IA).

**Fuentes autoritativas (aprobadas):** ADR `Verbara.Platform/docs/decisions/0029-typification-cascading-conditional-ai-module.md` + spec `docs/specs/2026-06-07-typification-cascading-conditional-ai.md`.

## Decisiones bloqueadas (forks + reconciliaciones resueltas)

- **Arquitectura:** Híbrido (Opción C) — módulo de 1ª clase `Verbara.Platform.Typification` (jerarquía+condicional+renderer dinámico), reusa `http_request` (data-dips P3), stack IA (P2) y contexto canal/cola/campaña. **NO** se modela como flow crudo.
- **Alcance P0:** núcleo manual. **Clean-break (sin back-compat, pre-launch):** se ELIMINA el dominio `Disposition` plano; `POST /conversations/{id}/wrapup` se reemplaza por `POST /conversations/{id}/typify` + `GET /conversations/{id}/typification-form`.
- **Licensing:** nuevo `LicenseFeature.AdvancedTypification = 1 << 9` (Pro). Incluido en el mask `All` **y en `SelfHostStartup`**. **Solo el diseñador `/admin/typification/*` se gatea**; los endpoints de runtime `/typify` + `/typification-form` **NO** se gatean (si no, un tenant sin licencia no podría cerrar conversaciones). Permiso RBAC: **nuevo `system:typification:configure`**.
- **Profundidad:** configurable por tenant, default 5, máx 8, validada en publish.
- **Migraciones:** **baseline squash completo** → colapsar `001..034` en un solo `001_Baseline.sql` (incluye las 3 tablas typification, DROP `dispositions`/`wrap_up_records`/`conversations.wrap_up`).
- **Reconciliaciones (del Plan agent):** (1) **MANTENER** el admin de `DispositionCode` de campaña en `campaign-detail-page.tsx` + `use-campaigns.ts` — es el Dialer de Pro, fuente de los `DialerCode` que las hojas bridgean; solo se elimina la disposition **plana de Platform** (`use-dispositions.ts` + rama global del wrap-up). (2) Evento cross-pod = **3 registros** (ApiJsonContext + PlatformPushJsonContext + switch de `RemoteEventDispatcher`). (3) `ConversationState.WrapUp` (enum de estado) **se queda**. (4) `IConversationLifecycleService.CloseAsync(..., WrapUpRecord? wrapUp, ...)` → el param `wrapUp` está muerto (6 call sites pasan null) → se elimina.

## Convenciones de ejecución

Subagent-Driven + FCM batching + review de dos etapas por tarea + 🔒 individual en riesgosas + **holística cross-repo final** (rigor que atrapó Criticals en W4/W5b). Conventional Commits, **sin `Co-Authored-By`/referencias a IA**. Native AOT (sin reflexión, source-gen), `TreatWarningsAsErrors`, Npgsql crudo, test naming `Method_ShouldExpected_WhenCondition`. Cross-repo coordinado. `finishing-a-development-branch` al cierre (**confirmando antes** de Push/PR). Plan mirror a `docs/plans/active/` tras aprobación; `git mv` a `completed/` al shippear.

## AOT pitfalls (explícito)

1. **Solo string-dict:** `FieldValues`/`Headers` = `IReadOnlyDictionary<string,string>`; enums tipados → dispatch estático; **nunca `Dictionary<string,object>`**.
2. **Registro JSONB:** todo tipo alcanzable por el wrapper `definition` en `PostgresJsonSerializer.cs`; submission reusa `IReadOnlyList<string>`/`IReadOnlyDictionary<string,string>`. Un miss = `NotSupportedException` en runtime / warning en publish.
3. **DTOs wire** en `ApiJsonContext`.
4. **Evento cross-pod = 3 registros** (Api + Push + RemoteEventDispatcher switch). Falta = pérdida silenciosa SSE (lección W4).

**Direction-inference:** `Conversation` no expone `Direction`; el resolver infiere outbound desde `Metadata` (`campaignId`/`callAttemptId`), resto inbound; queueId solo de `Owner` cuando `Kind==Queue`. Inferencia deliberada y documentada.
