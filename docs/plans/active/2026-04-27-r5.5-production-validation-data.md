## Industry research highlights (informa diseño)

### Tooling industry-standard adoptado

- **NBomber** (already shipped) — HTTP API load testing en .NET, AOT-compatible.
- **SIPp** — Industry standard SIP load tester. Sin RTP el load no es realista; con RTP scales hasta limit del Asterisk box.
- **Pumba** — Docker-native chaos engineering tool. Mata, pausa, slow disk, network chaos directo a containers. Más simple que Litmus/Chaos Mesh para Docker compose deployment (deferred a R6 cuando haya K8s).
- **Prometheus blackbox-exporter** — Self-hosted synthetic monitoring. Integra con `alerts.yml` existente. Multi-region upgrade a Grafana Cloud Synthetic en R5.6 si se justifica.
- **Linphone** — Industry softphone for spot-check audio E2E.
- **Google SRE PRR pattern** — Production Readiness Review checklist + SLO + error budget framework.

### Hardware benchmarks reales (research findings)

- Asterisk PJSIP en Xeon Quad-Core: 1,500-1,600 concurrent calls con RTP audio.
- Call recording cuts capacity significantly (~30-50%).
- CPU max load operacional: < 75% (industry standard).
- Re-INVITE direct media (P2P RTP): scales a 250+ calls @ 9% CPU on 1 GHz laptop.
- High-end multicore Xeon: 4,500+ concurrent calls (VitalPBX validation).

### Modern load test gating pattern

- **Smoke gate** (per PR): 50 VUs × 3 min (subset NBomber).
- **Full load gate** (merge a main): 30-60 min full suite.
- **Soak gate** (nightly o calendar): 2-24h al 70% peak load.
- **Endurance gate** (release validation): 24-48h sustained.

R5.5 ejecuta el `endurance gate` por primera vez. CI smoke/full integration deferred a R5.6.

## Principios de diseño (no-atajos)

1. **Datos reales antes de afirmar.** Si no medimos → marcamos "v2 measured pending" en lugar de inventar numero.
2. **Industry-standard tooling only.** SIPp / Pumba / blackbox-exporter / Prometheus / Grafana — todo open-source, adoptable por operators.
3. **Cada finding gets remediation.** Si C.2 chaos rompe algo, fix antes de cerrar Phase C.
4. **Reproducibility.** Todo automatizado vía scripts. Run mensual fácil después.
5. **Dual-output.** Cada doc tiene versión técnica (operators) + extracto marketing (sales).
6. **Hybrid local-first.** Desarrollar local (free + fast iteration), replicar cloud (representative datos), comparar ambos.
7. **Cero costo hasta cloud phase.** Phase 0L-E-L corren en máquina dev. Cloud VM solo durante Phase 0C-E-C (~5-7 días total).

### Phase A · Test infrastructure prep (1-2 días, after Phase 0L)

**A.1** Multi-tenant data seed scripts: `scripts/seed-staging.sh` que crea 3 tenants (Small/Medium/Large profiles) × 100 agents × 50 queues con realistic distribution. Resuelve el gap "load-test.sh assumes pre-seeded loadtest tenant".
**A.2** Fix `scripts/load-test.sh` tenant seed step (B.4 doc-lint finding from R5.4) — call seed-staging.sh first if tenant not present.
**A.3** SIPp scenarios for Asterisk side: 5 XML scripts en `tests/sipp-scenarios/`:
  - `01-basic-call.xml` — INVITE/ACK/BYE básico con RTP
  - `02-ivr-navigation.xml` — DTMF para menú IVR
  - `03-queue-join.xml` — caller entra a queue support, espera 30s, atendido por agent
  - `04-conference.xml` — 3-party conference setup + tear-down
  - `05-transfer.xml` — blind/attended transfer flow
**A.4** Setup `blackbox-exporter` con 5-10 critical user journeys: HTTP probes a `/health/ready`, `/api/v1/auth/login`, `/api/v1/queues`, `/api/v1/agents/me/presence`, `/scalar/v1`. Wire a alertmanager.
**A.5** Pumba chaos experiment definitions: 10 experiments documented en `tests/chaos-experiments/`:
  1. `pg-pause-30s` — pausa Postgres 30 seg
  2. `pg-kill-restart` — mata Postgres y verifica restart
  3. `redis-pause-30s` — pausa Redis 30 seg
  4. `redis-kill-restart` — mata Redis y verifica restart
  5. `asterisk-crash` — kill Asterisk container
  6. `platform-api-crash` — kill Platform.Api container
  7. `network-partition-pg` — bloquea Postgres networking 60s
  8. `slow-disk-pg` — disk latency injection 200ms
  9. `bandwidth-limit-rtp` — limit RTP bandwidth a 200 Kbps
  10. `packet-loss-rtp` — 5% packet loss en RTP traffic

### Phase B-L · Baseline measurement LOCAL (2-3 días, paralelizable después de Phase A)

## Phase structure rationale

- **Phase 0L first** — sin staging real no hay nada que medir. Local cero-costo permite iterar sin presión $.
- **Phase A para infra** — sin tenant seed + SIPp + chaos catalog + synthetic checks no podemos correr B-E correctamente.
- **Phase B-L baseline antes que C-L/D-L/E-L** — necesitamos saber el "normal" antes de stress/chaos/soak.
- **Phase D-L 24h corre paralelo a Phase E-L synthetic** — pueden compartir staging sin conflicto.
- **Cloud replication checkpoint mandatory** — si Phase L tests fallan, hacer cloud es desperdicio. Cloud solo cuando local works clean.
- **Phase D-C 48h vs D-L 24h** — diferencia explica leaks que solo aparecen sostenido. Cloud is "representative production", local is "uncontested ceiling".
- **Phase F final consolidation** — refresca docs con BOTH datasets (local + cloud) clearly distinguished.

## Cross-cutting discipline (aplica a TODAS las phases)

1. **Reproducibility:** todo automatizado vía scripts. NO manual one-off commands.
2. **Pre-snapshot before each chaos experiment:** Postgres + Redis snapshot pre + post + verified restorable.
3. **Prometheus retention:** 30 días local, 7 días cloud (cost-aware).
4. **Grafana dashboards exported as JSON:** committed to repo, can be re-imported.
5. **Cost monitoring:** AWS billing alarm at $30, $50, $80 thresholds. Auto-shutdown if exceeds.
6. **Findings-as-issues:** every chaos break / soak leak / synthetic fail → GitHub issue con label `r5.5-validation`.
7. **No production data:** staging usa fake data only. Explicit gate F.4 verifies.

## Riesgos identificados + mitigación

| Riesgo | Probabilidad | Impacto | Mitigación |
|---|---|---|---|
| Local staging usa demasiado RAM/disk de dev machine | Alta | Bajo | Documenta requirements (16 GB RAM + 50 GB disk free) en P0L.1; gate antes de Phase B-L |
| Cloud VM costo excede $80 (Phase D-C 48h soak corre más por bug) | Media | Bajo ($) | Auto-shutdown cron en P0C.3 + AWS billing alarm |
| Phase B-L reveals NBomber HTTP scenarios irrelevant if real bottleneck en Asterisk | Media | Medio | Por eso A.3 SIPp scenarios — cubre el lado complementario; B-L.4 cross-correlation reveals which side |
| Phase D-L/D-C soak descubre leak severo que requiere Pro/Platform code fix | Media | Alto | Si fix < 1 día → inline; si > 1 día → defer R5.6 + document leak; spec doesn't promise fix |
| Pumba chaos rompe staging recurrently y bloquea Phase D | Media | Medio | Phase C-L/C-C después de B-L/B-C baseline; pre-snapshot Postgres antes de cada chaos exp; Phase D corre AFTER Phase C closure |
| Cold-clone smoke F.4 falla con setup wizard como B.4 ya descubrió | Alta | Bajo | Fix inline en Phase A (A.2 already addresses) |
| Local + cloud datasets divergen significativamente | Alta | Medio | EXPECTED — ambos sets se documentan separadamente. Cloud es authoritative para SLOs/capacity (representative); local es "ceiling" comparison |
| 48h cloud soak acapara staging mientras E-C synthetic monitoring corre | Baja | Bajo | E corre paralelo; synthetic checks toleran transient errors |
| User decision changes mid-execution (e.g., wants real trunk after all) | Baja | Bajo | Spec gates D-FORCEs explicitly; mid-execution course-correct documented in spec amendment |
