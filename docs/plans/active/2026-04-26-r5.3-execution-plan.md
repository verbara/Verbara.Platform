### Task P0.1 — Author ADR-0006 (Platform) "Audit entries schema normalization"

**Files:**
- Create: `Asterisk.Platform/docs/decisions/0006-audit-entries-schema-normalization.md`

**Mode:** foreground (coordinator-authored, ADRs require human judgment).

**Why TDD doesn't apply:** Documentation file. Verification = file exists + structure matches existing ADR template + 4 mandatory sections present.

- [ ] **Step 1: Read existing ADR style**
  Read: `Asterisk.Platform/docs/decisions/0002-tenant-stamping-pipeline-end-to-end.md` and `0004-tenant-stamping-execution-conventions.md` for canonical sections (Status / Date / Deciders / Related / Context / Decision / Decision space / Rationale / Consequences / Alternatives / References).

- [ ] **Step 2: Write ADR-0006 with these sections:**
  - **Status:** Accepted (executed during R5.3 Phase 0)
  - **Date:** 2026-04-26
  - **Related:** ADR-0002 (tenant-stamping policy parent), ADR-0004 (per-package conventions)
  - **Context:** `AuditEntry` C# model carries `Category`, `Severity`, `ActorType`, `Changes` (with `BeforeJson` / `AfterJson` snapshots) + `IntegrityHash`. `PostgresAuditStore.cs:23-37` insert SQL ignores these fields — only persists `entry_id, tenant_id, action, entity_type, entity_id, performed_by, details JSONB, occurred_at, impersonator_id`. Result: structured audit information lost or buried in `details` JSONB blob without contract. Audit Log Viewer (R5.2 PB.x) frontend dropdown filters by `severity`/`category` have no backing index.
  - **Decision:** Promote `Category`, `Severity`, `ActorType`, `BeforeJson`, `AfterJson`, `IntegrityHash` to first-class typed columns via `V012_AuditEntriesNormalize.sql`. Add CHECK constraints + indexes per `(tenant_id, severity, occurred_at)` and `(tenant_id, category, occurred_at)`. Update writer/reader. Backwards compat: legacy `Metadata` dict sigue serializandose en `details` JSONB.
  - **Decision space:**
    - **(a) Normalize (chosen):** typed columns + indexes + writer/reader update
    - **(b) JSONB-only path:** GIN indexes sobre `details->>'severity'` etc. — query plan worse + viewer code más complejo
    - **(c) Acceptable status quo:** defer to R6
  - **Rationale:**
    - SOC 2 audit log integrity story; JSONB-only debilita compliance narrative
    - Audit Viewer R5.2 ya espera campos typed; UI tiene dropdown `severity` filter sin backend que lo soporte rápido
    - 1 sola migration ahora vs migration + index rebuild later cuando hay 100M+ rows
    - `IntegrityHash` (audit tamper-evidence) requiere columna dedicada
  - **Consequences positive:** 10-100x query perf via indexes; SOC 2 compliance refuerza; audit viewer drawer Before/After tab renderiza sin JSON deep-parse en frontend.
  - **Consequences negative:** +50-200 bytes per row storage; +2-3% insert latency (negligible); migration window required (atomic safe <100k rows; batch pattern documented for >10M).
  - **Alternatives considered:** see Decision space.
  - **References:** ADR-0002, ADR-0004, R5.3 spec §"D-FORCE-2", `Asterisk.Platform/src/Asterisk.Platform.Storage.Postgres/Stores/PostgresAuditStore.cs:23-37`.

### Task P0.2 — Author ADR-0007 (Platform) "Agent tenant resolver strict mode builder"

**Files:**
- Create: `Asterisk.Platform/docs/decisions/0007-agent-tenant-resolver-strict-mode-builder.md`

**Mode:** foreground.

- [ ] **Step 1: Write ADR-0007 with these sections:**
  - **Status:** Accepted (executed during R5.3 Phase 0).
  - **Date:** 2026-04-26
  - **Related:** ADR-0005 (cross-tenant SignalR subscription validation parent)
  - **Context:** `IAgentTenantResolver?` actualmente optional con default null en `PlatformHub` constructor (Pro.Push.SignalR `Hubs/PlatformHub.cs:70,82`). Sin resolver registrado, hub permite cross-tenant subscription sin check (legacy permissive behavior preserved at line 268: `if (_tenantResolver is not null) { ... }` guard). ADR-0005 §"Concerns" documenta esto pero sin path a remediation. Production deployments olvidan registrar el resolver y obtienen zero protection silenciosamente.
  - **Decision:** Agregar `WithStrictMode(bool enabled = true)` builder extension method a `ProPushBridgeBuilder` en `Asterisk.Sdk.Pro.Push.SignalR.DependencyInjection.ProPushBridgeBuilderExtensions`. Registrar `IPlatformHubStrictModePolicy` singleton (NEW interface). Hub `OnConnectedAsync`:
    - If `policy.StrictModeEnabled && _tenantResolver is null` → throw `InvalidOperationException("Strict mode requires IAgentTenantResolver registration")`.
    - Else if `_tenantResolver is null && multiTenantContext` → emit warning log "PlatformHub: IAgentTenantResolver not registered — cross-tenant subscriptions are permissive (legacy behavior). Register resolver or call WithStrictMode() to fail-fast."
  - **Decision space:**
    - **(a) Required-by-default:** breaking change para hosts que no lo registran (semver bump major hint en Pro)
    - **(b) `WithStrictMode()` builder opt-in (chosen):** preserva backwards compat + path opt-in seguro + warning log no-silent-failure
    - **(c) Status quo:** sigue como foot-gun production-unsafe
  - **Rationale:**
    - (a) viola "0 breaking changes en minors" principle establecido en Pro roadmap
    - (b) preserva backwards compat + da path opt-in seguro + warning log alerta operators
    - (c) deja foot-gun production-unsafe → contradice "no atajos, todo en pro del producto final"
  - **Consequences positive:** backwards compat preservada en R5.3; production safety opt-in; R5.4 puede flip default sin sorpresa (operators ya recibieron warning logs en R5.3).
  - **Consequences negative:** opt-in still missable; warning log adds noise to single-tenant hosts (mitigated by log-only-if multi-tenant context heuristic).
  - **Migration guide:** R5.3 release notes: "Production deployments SHOULD call `.WithStrictMode()` after `AddProPushBridges()`. R5.4 will flip default to strict-mode + emit warning if not opted-out via `.WithLegacyPermissiveMode()`."
  - **References:** ADR-0005 §"Concerns", `Asterisk.Sdk.Pro/src/Asterisk.Sdk.Pro.Push.SignalR/Hubs/PlatformHub.cs:70-82,253-298`.
