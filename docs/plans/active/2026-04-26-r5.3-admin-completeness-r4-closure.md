## DB schema migration deep dive (D-FORCE-2)

**File:** `/media/Data/Source/IPcom/Asterisk.Platform/src/Asterisk.Platform.Storage.Postgres/Migrations/V012_AuditEntriesNormalize.sql`

```sql
-- =============================================================================
-- V012: Audit entries schema normalization (R5.3 — ADR-0006)
-- =============================================================================
-- Promotes 4 previously-JSONB-blob fields to first-class typed columns:
--   category, severity, actor_type, before_json, after_json + integrity_hash
-- Backfills from `details` JSONB best-effort for legacy rows.
-- Adds CHECK constraints + indexes for Audit Viewer filter performance.
-- =============================================================================

BEGIN;

-- Stage 1: Add nullable columns first (safe for live writes during migration)
ALTER TABLE audit_entries ADD COLUMN IF NOT EXISTS category TEXT;
ALTER TABLE audit_entries ADD COLUMN IF NOT EXISTS severity TEXT;
ALTER TABLE audit_entries ADD COLUMN IF NOT EXISTS actor_type TEXT;
ALTER TABLE audit_entries ADD COLUMN IF NOT EXISTS before_json JSONB;
ALTER TABLE audit_entries ADD COLUMN IF NOT EXISTS after_json JSONB;
ALTER TABLE audit_entries ADD COLUMN IF NOT EXISTS integrity_hash TEXT;

-- Stage 2: Backfill from details JSONB blob (best-effort)
DO $$
DECLARE
    backfilled INTEGER;
    defaulted INTEGER;
BEGIN
    UPDATE audit_entries
    SET category   = COALESCE(details->>'category',   'config'),
        severity   = COALESCE(details->>'severity',   'info'),
        actor_type = COALESCE(details->>'actor_type', 'system'),
        before_json = details->'before',
        after_json  = details->'after',
        integrity_hash = details->>'integrity_hash'
    WHERE category IS NULL;
    GET DIAGNOSTICS backfilled = ROW_COUNT;

    SELECT COUNT(*) INTO defaulted FROM audit_entries
    WHERE category = 'config' AND (details->>'category') IS NULL;

    RAISE NOTICE 'V012: backfilled % rows; % rows defaulted to category=config (no JSONB hint).',
                 backfilled, defaulted;
END $$;

-- Stage 3: NOT NULL + CHECK constraints + indexes
ALTER TABLE audit_entries ALTER COLUMN category SET NOT NULL;
ALTER TABLE audit_entries ALTER COLUMN category SET DEFAULT 'config';
ALTER TABLE audit_entries ALTER COLUMN severity SET NOT NULL;
ALTER TABLE audit_entries ALTER COLUMN severity SET DEFAULT 'info';
ALTER TABLE audit_entries ALTER COLUMN actor_type SET NOT NULL;
ALTER TABLE audit_entries ALTER COLUMN actor_type SET DEFAULT 'system';

ALTER TABLE audit_entries ADD CONSTRAINT chk_audit_severity
    CHECK (severity IN ('info','warn','error','critical'));
ALTER TABLE audit_entries ADD CONSTRAINT chk_audit_category
    CHECK (category IN ('auth','billing','config','tenant','security','impersonation','retention','data'));
ALTER TABLE audit_entries ADD CONSTRAINT chk_audit_actor_type
    CHECK (actor_type IN ('user','system','impersonator','service-account'));

CREATE INDEX IF NOT EXISTS idx_audit_severity
    ON audit_entries (tenant_id, severity, occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_category
    ON audit_entries (tenant_id, category, occurred_at DESC);

COMMIT;

-- =============================================================================
-- Rollback (manual):
--   ALTER TABLE audit_entries DROP COLUMN category, severity, actor_type,
--                                          before_json, after_json, integrity_hash;
--   DROP INDEX idx_audit_severity, idx_audit_category;
-- =============================================================================
```

**Concurrent-write safety:** Atomic transaction safe en deploys <100k rows. Para >10M rows: Stage 1 en transaction separada (ADD COLUMN NULL no toma lock prolongado), Stage 2 en batches de 10k via LIMIT loop, Stage 3 en mantenimiento window. Pattern documentado en `docs/operations/migrations.md` (Phase C output).

**Writer update — `PostgresAuditStore.cs`:**

```csharp
const string sql = @"
    INSERT INTO audit_entries
        (entry_id, tenant_id, action, entity_type, entity_id,
         performed_by, details, occurred_at, impersonator_id,
         category, severity, actor_type, before_json, after_json, integrity_hash)
    VALUES (@EntryId, @TenantId, @Action, @EntityType, @EntityId,
            @PerformedBy, @Details::jsonb, @OccurredAt, @ImpersonatorId,
            @Category, @Severity, @ActorType, @BeforeJson::jsonb, @AfterJson::jsonb, @IntegrityHash)";

var parameters = new {
    // ... existing 9 fields ...
    Category      = entry.Category ?? "config",
    Severity      = entry.Severity ?? "info",
    ActorType     = entry.ActorType ?? "system",
    BeforeJson    = entry.Changes?.Before is not null
                    ? JsonSerializer.Serialize(entry.Changes.Before, AuditJsonContext.Default.JsonElement)
                    : null,
    AfterJson     = entry.Changes?.After is not null
                    ? JsonSerializer.Serialize(entry.Changes.After, AuditJsonContext.Default.JsonElement)
                    : null,
    IntegrityHash = entry.IntegrityHash,
};
```

**Reader update:** hidrata `AuditEntry.Changes` desde `before_json` + `after_json` columnas; mapea `category`/`severity`/`actor_type` directamente a properties typed; `Metadata` dict sigue desde `details` JSONB (backwards compat).

**Audit Viewer wins post-migration:**
- `GET /api/v1/management/audit/events?severity=critical` usa `idx_audit_severity` (10-100x faster vs JSONB parse + filter)
- `GET /api/v1/management/audit/events?category=billing` similar via `idx_audit_category`
- Audit Log Viewer drawer "Before / After" tab renderiza desde 2 columnas typed sin deep-parse en frontend

## ADR shapes (Phase 0 deliverables)

### ADR-0006 — `audit-entries-schema-normalization`

**Status:** Accepted (R5.3 Phase 0)
**Decision:** Promover `Category`, `Severity`, `ActorType`, `BeforeJson`, `AfterJson`, `IntegrityHash` de JSONB blob a columnas typed. V012 migration + writer + reader + indexes.
**Rationale:** SOC 2 audit log integrity story; 10-100x query perf via indexes; audit viewer filter UX requires typed fields. Single migration ahora vs migration+rebuild later cuando hay 100M+ rows.
**Consequences:** +50-200 bytes per row storage; +2-3% insert latency (negligible); zero API surface change; backwards compat preservada (legacy `Metadata` dict sigue en JSONB).

### ADR-0007 — `agent-tenant-resolver-strict-mode-builder`

**Status:** Accepted (R5.3 Phase 0)
**Decision:** Agregar `WithStrictMode(bool enabled = true)` builder extension a `ProPushBridgeBuilder` + `IPlatformHubStrictModePolicy` singleton. Hub `OnConnectedAsync` throw `InvalidOperationException` si strict + resolver null; warning log si non-strict + resolver null en multi-tenant context.
**Rationale:** (a) required-by-default rompe "0 breaking changes en minors". (c) status quo deja foot-gun. (b) preserva backwards compat + opt-in path + warning log no-silent-failure.
**Consequences:** Backwards compat preserved en R5.3; production safety opt-in; R5.4 puede flip default sin sorpresa (operators ya recibieron warning logs).

### ADR-0001 (Promotion) — `consumer-dual-prong-dependency-pattern`

**Status:** Proposed → **Accepted** (R5.3 Phase 0)
**Action:** Single-line status field edit + §"Validated by R5.2 ship" footnote citing Platform 1.11.0 consuming Pro.Push.SignalR + Pro.Analytics + SDK Cluster.Primitives directly (3 examples).
**No code change.**
