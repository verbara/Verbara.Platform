## Scope total · 13 execution items + 4 closure deliverables

### Track A · Performance & SLOs (3 items, ~1 sem paralelizable)

**S5.1 · Load test baseline** — M
- Suite NBomber (.NET-native, AOT-compatible) en proyecto opt-in `tests/Asterisk.Platform.LoadTests/` (no en slnx default)
- 5 escenarios: JWT issuance/validation throughput · Queue ingestion (1,000 calls/min) · Realtime presence broadcast (3-node × 500 agents) · LiveQueueSnapshotWriter (5 Hz × 100 queues) · AgentAssist session start/STT throughput
- Output: JSON + Markdown summary auto-generado en `docs/operations/load-test-baseline.md`
- Reproducible: `scripts/load-test.sh` con `docker/docker-compose.loadtest.yml`
- Salidas alimentan **S5.7** (capacity planning) y **S5.2** (SLOs basados en datos reales)

**S5.2 · SLO definitions** — S
- `docs/operations/slos.md`: availability targets (99.5% baseline / 99.9% enterprise), latency p50/p95/p99 por endpoint crítico, error rate ceiling per service class
- Source attribution: cada SLO referencia explícitamente meter/counter de los 17 Pro meters + Platform meters que lo mide
- Dependencia: después de S5.1 first run

**S5.3 · Prometheus alert rules baseline** — S
- `docs/operations/alerts.yml` con 15-20 reglas pre-configuradas
- Severity classification: P0 page on-call (API availability < 99%, JWT validation latency p99 > 500ms, license guard blocked > 1%, retention service stalled > 1h) · P1 ticket within 24h · P2 review weekly
- Cada alerta: 1 párrafo runbook entry "what / why / first response" en `docs/operations/alerts-runbook.md`
- Validation: cargar reglas en Prometheus de staging y verificar parsing
- Dependencia: después de S5.2

### Track B · Security & Compliance (2 items, ~1 sem)

**S5.4 · Internal security audit + remediation** — M (subagent-driven)
- 4-5 subagents paralelos con scope checklist:
  1. **OWASP Top 10 web** (SQL injection, XSS, broken auth, broken access control, etc.) — OWASP ZAP automated baseline + manual review endpoints sensibles
  2. **Multi-tenant isolation** — verificar NO leakage cross-tenant en endpoints, SignalR groups, audit log queries, retention purges (input ADR-0002/0004/0005 R5.2)
  3. **JWT + MFA + impersonation** — token validation, refresh flow, MFA bypass attempts, impersonation audit completeness
  4. **Audit log integrity** — append-only enforcement, timestamps non-tamperable, sensitive field redaction
  5. **Secrets handling** — DataProtection wrap correcta, no plaintext en config/logs/audit, key rotation tested
- Tools: OWASP ZAP (Docker baseline + active scan) + Burp Community (manual probing) + sqlmap (specific endpoints) + manual code review de `/management/*` + `/api/v1/admin/*`
- Deliverables: `docs/security/internal-audit-2026-04.md` + `docs/security/audit-checklist.md` + `scripts/run-zap-scan.sh`
- Findings: tracked como GitHub issues con label `security-audit-r5.4`, severity P0/P1/P2/P3
- **Gate:** P0/P1 fixed antes de C.1 release. P2/P3 → tickets v1.13.x patches.

**S5.9 · JWT multi-key rotation completion** — M
- Cierra C.1 del post-R5.1 triage; v1.9.2 dejó parcial impl single-key
- `IJwtKeyRotationService` + impl en `Asterisk.Platform.Auth/Jwt/`
- `JwtBearerOptions.TokenValidationParameters.IssuerSigningKeys` populated con multiple keys (old + new) durante rolling window 24h default
- Endpoint `POST /api/v1/management/security/jwt/rotate-key`: genera new key, activates new (old stays valid grace period), audit `security.jwt.key_rotated`, observable `jwt.keys.active` gauge + `jwt.key.rotation.duration` histogram
- Integration con `Asterisk.Platform.Identity.Redis` (R5.1) — keys cachean cross-cluster vía nuevo `RedisJwtKeyStore`
- RBAC: nueva permission `security.jwt.rotate` (PlatformAdmin only)
- Tests: +5 unit + 1 integration (Testcontainers Redis) + 1 E2E rotation con 2 nodes simulados — zero downtime claim verified

## ADRs gating R5.4

**ADR-0008 · Internal security audit baseline + checklist** (Platform)
- **Decision:** R5 train cierra con audit interno (no externo) per D-FORCE-1 user input. Audit sigue checklist OWASP Top 10 + 4 áreas Asterisk-específicas (multi-tenant isolation, JWT/MFA/impersonation, audit log integrity, secrets handling).
- **Rationale:** Sin contrato enterprise hoy que justifique vendor externo. Audit interno con subagent-driven approach es rigurosa y rápida; vendor externo se contrata post-R5 cuando demanda concreta aparezca.
- **Consequences:** No hay "redacted public security report" como sales asset hasta vendor externo (R6 o ad-hoc). Findings tracked internamente.
- **Status:** Accepted

**ADR-0009 · SLO baseline + alert severity model** (Platform)
- **Decision:** SLOs derivados de S5.1 load test results reales (no aspirational). Alert severity model 3-tier: P0 page on-call (availability/critical-path), P1 ticket 24h (SLO breach), P2 review weekly (capacity/slow queries).
- **Rationale:** Aspirational SLOs (común en specs early-stage) producen alert fatigue + false confidence. Datos reales primero, target después.
- **Consequences:** Algunos SLOs iniciales pueden ser más conservadores que ideales; documentar como "v1 baseline" con path a "v2 enterprise" cuando hardware/scale justifique.
- **Status:** Accepted
