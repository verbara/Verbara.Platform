## Context

R5.2 is the second release of the R5 train (post-D-FORCE-2 split: R5.1 Production Readiness + R5.2 Security Admin + R5.3 Admin Completeness + R5.4 Production Validation). Original release train scope was 5 features (S3.1-S3.5) targeting "SOC 2 readiness" narrative. Post-R5.1 triage surfaced **7 carry-forward tickets** (Set B) derived from R5.1 limitations.

**During Wave 2 audit (2026-04-25)** of the four Pro packages most exposed to multi-tenant state (Pro.AgentAssist, Pro.CallAnalytics, Pro.EventStore, Pro.Push.SignalR), three **P0/P1 violations** of ADR-0002 tenant-stamping policy were discovered — all distinct from B.1 but sharing the same root pattern:

- **Pro.EventStore P0:** `EventStoreSubscriber.cs:117` initializes `tenantId = ""` and falls back to `session.TenantId ?? ""` if the cache miss occurs. Identical bug class to R5.1 B.1.
- **Pro.CallAnalytics P1:** `CallAnalyticsEngine.cs:183` creates fallback `CompletedSessionRow` with `TenantId = serverId` when the CDR is missing — cross-tenant data leak in multi-server deployments.
- **Pro.Push.SignalR P0 (security):** `PlatformHub.SubscribeToAgentPresenceAsync` accepts any `agentId` without validating that the agent belongs to the supervisor's tenant — cross-tenant info leak.

These shift R5.2 from "5 features + 7 carry-forwards = 12 items" to **~18-19 items**. The user-approved cadence option was **expand R5.2 to 2.5-3 sem** rather than descope or accept rough edges. R5.2 absorbs the audit findings as a Phase 0 mega-track.

**Goal:** ship Pro 1.13.0-pro + Platform 1.11.0 + Web 1.10.0 with: (a) tenant-stamping pipeline complete across 4 Pro packages + Platform + Web; (b) full security admin surface (MFA admin/wizard, audit viewer, impersonation, retention); (c) all 7 R5.1 carry-forward tickets resolved.

## Phase 0 — Foundation (5-7 días)

### P0.1 — ADR-0004 (Platform) "Tenant stamping execution conventions per-package"
- **Mode:** foreground (authored by user/coordinator)
- **Output:** `docs/decisions/0004-tenant-stamping-execution-conventions.md`
- **Companion to:** ADR-0002 (policy-level)
- **Documents:**
  - Pro.EventStore: events MUST include `TenantId` in payload; subscriber rejects events with empty/null `TenantId` (fast-fail with structured log).
  - Pro.CallAnalytics: `CallAnalyticsEngine` injects `ITenantContext`; `ICompletedSessionStore.GetAsync(tenantId, sessionId)` signature locked; no `serverId` fallback.
  - Pro.Push.SignalR: hub methods that subscribe to other tenants' state MUST validate ownership via `IAgentTenantResolver` (per ADR-0005); bridges require explicit `WithDefaultTenantId()` builder call (no implicit `"default"`).
  - Observability tag patterns: `AsteriskSemanticConventions.Tenant` mandatory in spans; meter `tenant_id` dimension required where cardinality permits.
- **Status at write:** Accepted (executed during Phase 0).

### P0.1.b — ADR-0005 (Platform) "Cross-tenant subscription validation in SignalR hubs"
- **Mode:** foreground
- **Output:** `docs/decisions/0005-cross-tenant-signalr-subscription-validation.md`
- **Decision:** caché de 5 min de tenant ownership (`IAgentTenantResolver`) con invalidation lateral via Pro.Push event (`agent.tenant.membership.changed`). Default rejected: (a) JWT claim trust-only — insufficient because tenant membership can change after token issuance; (b) database round-trip per call — too expensive at scale.
- **Status at write:** Accepted (executed during Phase 0).

### P0.2 — Schema migrations bundle V00X
- **Mode:** 1 background subagent
- **Output:** 5 SQL migration files
  - Pro.Analytics.Storage.Postgres `V006__live_queue_snapshots_tenant_check.sql`
  - Pro.EventStore.Postgres `V003__events_completed_tenant_check.sql` (V001 was monolithic; V003 is increment)
  - Pro.AgentAssist.Storage.Postgres `V002__agentassist_tenant_check.sql`
  - Pro.CallAnalytics.Storage.Postgres `V002__callanalytics_tenant_check.sql`
  - Platform `V0XX__data_protection_keys.sql` (per ADR-0003)
- **Pattern per Pro package:**
  ```sql
  -- Purge legacy empty rows + add CHECK
  DELETE FROM <schema>.<table> WHERE tenant_id = '';
  ALTER TABLE <schema>.<table>
    ADD CONSTRAINT chk_tenant_id_nonempty CHECK (tenant_id <> '');
  ```
- **Rollback path:** documented per migration; idempotent so re-runs safe.
- **Tests:** +2 IT (Testcontainers verifies CHECK rejects empty insert + DELETE preserves non-empty).

## Risks / mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Phase 0 mega-track scope slips → cascade delays Phase A/B/C | Medium | Phase 0 has 10 sub-tasks but most are independent (4 DI refactors + observability + DataProtection + RBAC + Web stubs all parallel after schema bundle + ADR). 5-7 días buffer realistic. |
| Subagent rate limit (memory: v1.9.1 hit rate-limit with 4 background subagents) | Medium | Stagger: launch Phase 0 subagents 2-3 at a time, not all 6 at once. Phase A/B/C overlap caps at 10 concurrent — still within observed limits. |
| Pro 1.13.0-pro breaking-fix surprises an external Pro consumer | Low | We are the only Pro consumer today (Platform). Mitigation moot. CHANGELOG annotates clearly for any future external consumer. |
| Recovery codes crypto bug introduces auth bypass | Low | Use `RandomNumberGenerator.GetBytes` (not `Random`); hash+salt before storage; comprehensive unit tests covering invariants. Code review required for PA.2. |
| Audit viewer DataTable virtualized fails on >10M rows in production | Medium | Backend already paginates; virtualizer renders ~50 rows at a time. Performance test with synthetic 1M-row DB before ship in PD.2. |
| Impersonation auto-timeout `IHostedService` adds startup risk | Low | Standard pattern; copy from existing v1.x.x background services. Health check tag `"ready"` per CLAUDE.md cross-cutting discipline. |
| B.18 flaky tests fix doesn't actually stabilize CI | Low-Medium | 10-PR validation gate before declaring B.18 done. If still flaky, document additional root-cause investigation in PD.1 amendment. |
