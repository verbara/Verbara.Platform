# Platform v1.11.0 release runbook

Operator checklist for deploying Platform v1.11.0 (R5.2 "Security Admin +
Compliance"). Review every section before promoting to production. Each step is
idempotent unless explicitly noted.

---

## Pre-deploy

1. Take a Postgres backup (`pg_dump` of the platform DB plus any per-tenant
   sharded DBs).
2. Run `dotnet run --project tools/Verbara.Platform.Cli -- doctor --connection ...`
   on the target environment to confirm baseline schema is healthy.
3. Confirm the deployer has the `CONNECTION_STRING` for the platform DB exported
   in their shell (or available via `.env`).

---

## Deploy

1. Stop the API processes (or roll the deployment so only one node serves
   traffic at a time).
2. Apply the database migrations:
   ```bash
   dotnet run --project tools/Verbara.Platform.Cli -- migrate --connection "$CONNECTION_STRING"
   ```
3. Restart the API processes on the new image.

---

## Post-deploy

### 1. Re-seed RBAC permissions for existing tenants (R5.2 PC.3)

R5.2 introduces 7 new permissions:

- `security.mfa.admin`
- `audit.read`
- `audit.export`
- `security.impersonation.manage`
- `retention.read`
- `retention.manage`
- `tenant.settings.write`

Fresh tenants pick them up via `RoleTemplateSeeder` on first init.
**Existing tenants need manual migration** since per-tenant role permissions
are cloned once by `RbacMigrationSeeder` and never re-aligned automatically.

#### Step 1 — Identify existing tenants

```bash
psql "$CONNECTION_STRING" \
  -c "SELECT tenant_id, name, status FROM tenants WHERE status = 0 ORDER BY tenant_id;"
```

`status = 0` corresponds to `TenantStatus.Active`.

#### Step 2 — Run the re-seed CLI

For all active tenants:

```bash
export CONNECTION_STRING='Host=localhost;Database=asterisk_platform;Username=postgres;Password=postgres'
./scripts/reseed-rbac.sh --all
```

For specific tenants only:

```bash
./scripts/reseed-rbac.sh --tenants tenant-a,tenant-b
```

The script forwards arguments to `tools/RbacReseed/`. The same connection
string can be passed inline via `--connection` if you do not want to rely on
the env var.

#### Step 3 — Verify

```bash
psql "$CONNECTION_STRING" -c "
  SELECT permission_id
  FROM tenant_role_permissions
  WHERE tenant_id = 'tenant-a' AND role_id = 'platform_admin'
  ORDER BY permission_id;"
```

The output for any tenant whose `platform_admin` role was re-seeded should
include all 7 R5.2 keys listed above.

#### Behavior notes

- The CLI is **idempotent**: a second run after the first prints
  `aligned (no changes)` for every tenant.
- Each tenant is processed in its own transaction, so a failure on tenant N
  does not corrupt tenants 1..N-1.
- Tenants without a `platform_admin` role row are skipped (re-run the
  `RbacSeederOrchestrator` in the API for those tenants first; this is
  expected only for legacy installs from before R3).

### 2. Re-enter AgentAssist provider credentials (ADR-0003)

Persistent DataProtection keyring (Postgres-backed) shipped in R5.2 P0.8. Any
upgrade path that previously used the in-memory keyring will lose the
credentials encrypted with those ephemeral keys. Operators must re-enter the
following in the admin UI (`/admin/integrations/agent-assist`):

- Deepgram API key
- Whisper / Azure Whisper key
- Google Speech key
- ElevenLabs / Azure TTS key

This is a one-time tax; subsequent restarts preserve credentials because the
keyring rows now live in Postgres.

### 3. Smoke checks

1. `GET /health/ready` returns 200 with all checks healthy.
2. Log in as a `platform_admin` user and confirm the new R5.2 admin pages
   render without 403:
   - `/admin/security/mfa`
   - `/admin/audit`
   - `/admin/retention`
3. Confirm API key creation, listing, and reveal-once flow still work
   (`/admin/api-keys`).

## Rollback

1. Stop the API processes.
2. Restore the Postgres backup taken in pre-deploy step 1.
3. Re-deploy the previous image.
4. The RBAC re-seed is **forward-only safe** — re-running it against an older
   schema is harmless because the canonical permission list reverts together
   with the source code and only the rows present in the older `AllPermissions`
   list will ever be inserted.

### Rollback asymmetry — DataProtection-wrapped MFA enrollment material

> **Standing note, not v1.11-specific.** It applies to **any** rollback that crosses the
> release which shipped the `encrypt-mfa-secrets-at-rest` change (`decision_ref`
> [ADR-0003](../decisions/0003-dataprotection-key-persistence-strategy.md) — see that ADR's
> protected-column register addendum). Read it before reverting the API image across that
> boundary.

That change wraps `users.mfa_secret` and every element of `users.mfa_recovery_codes` with
`IDataProtection` on write, and a one-shot idempotent `UserMfaEncryptionMigrator` converts
pre-existing rows on the first boot of the new binary. Rolling **forward** is safe in both
directions of the deploy window: legacy rows still authenticate through the store's verbatim
fallback for the seconds the migrator scan takes. Rolling **back** is not symmetric.

**What breaks on rollback.** Reverting to the previous image **leaves the wrapped rows in place**
— nothing rewrites them back to plaintext. The old binary has no unwrap step, so it reads the
ciphertext as an ordinary string and hands it to `MfaService.VerifyCode`, which then computes a
TOTP code from ciphertext instead of from the shared secret and **returns false**. The same
applies to recovery-code redemption. The old binary does **not** throw, log an error, or fail a
health check — **MFA verification simply stops succeeding for every user the migrator already
converted**, silently. Users whose rows the migrator had not yet reached are unaffected.

**What does not break.** Non-MFA authentication is unaffected in **both** directions. Password
login, JWT issue/validate, API keys, RBAC, and every non-MFA field of the user row are untouched
by the wrap — the change is confined to two columns.

**There is no schema rollback**, because the change ships **no schema migration**: `mfa_secret
TEXT` and `mfa_recovery_codes TEXT[]` are unbounded and hold the longer ciphertext as-is, and no
index covers either column. Restoring a pre-deploy Postgres backup (Rollback step 2 above) is
therefore *not* required by this change, and reverting the binary alone will not undo it.

**Supported responses, in order of preference:**

1. **Roll forward.** Re-deploy the new image. Wrapped rows unwrap again and MFA verification
   resumes immediately — no data step, no migrator re-run needed beyond the ordinary boot scan.
2. **Admin-reset the affected users.** If the rollback must stand, reset MFA per user via
   `MfaAdminService.ResetMfaAsync` (`POST /management/mfa/users/{id}/reset`, behind the
   `MfaAdminGate` policy). Each user re-enrolls from scratch; every reset is audited. There is no
   bulk variant — script the per-user call if the enrolled population is large.
3. **Restoring the pre-deploy backup** also works (it predates the wrapping) but discards every
   write since the deploy, so it is a last resort and only defensible if you are rolling back for
   an unrelated reason that already requires it.

Do not attempt to "decrypt in place" with ad-hoc SQL — the plaintext is recoverable only through
the DataProtection keyring, which is exactly what the new binary does for you in option 1. See
[`backup-disaster-recovery.md`](backup-disaster-recovery.md) §1.6 for the keyring's own
backup/loss posture.
